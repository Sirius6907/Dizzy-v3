# v1.3.7 — "One Tap" (build 1039)

Branch `prism/v2-reskin` · 2026-11-26

This is the follow-through on "One App". v1.3.6 made the pieces behave like one
app; v1.3.7 removes the last place where the person was asked to do the app's
homework. Five privacy switches became one honest screen with one button, the
legal text stopped claiming titles never leave the phone, and an old build now
gets a poster with a way forward instead of an unreadable dialog.

Same rules as every release: nothing is pushed, tagged, released or deployed
without the owner saying go. The tag in this repo is local until he does.

---

## What ships in the build

- **One-tap consent gate** (`consent_onboarding_sheet.dart`) — replaces the
  4-switch sheet. Icon header, one lead paragraph, three "why" blocks
  (Troubleshooting / Monitoring / Backend operations), a straight-answer box on
  titles, one `Accept Terms & Privacy` button, and a link to the full text.
  Accepting sets all five consents on in one tap — four `CloudAuthService`
  consents plus `HeartbeatService` — then marks onboarding done and records the
  legal acceptance.
- **Mandatory, not dismissible** — shown after the P2P card and the username
  gate, with `isDismissible: false` / `enableDrag: false`. No close button, no
  decline button. Every local write behind the button is individually
  best-effort, so a failed preference write closes the gate rather than
  trapping someone on a screen with no exit.
- **Re-prompts are explicit** — when `LegalTerms.version` moves past what this
  install agreed to, the same screen opens and says, in the screen, that
  accepting switches all five back on including switches previously turned off,
  and that Settings → Privacy is where to turn any of them off again.
- **Settings → Privacy is unchanged as the withdrawal path** — still five
  switches, and turning one off still stops that upload immediately.
- **Legal text corrected** (`legal_terms.dart`, version `2026-11-26`) —
  `user_events` stores the titles you play, add, rate and search for, so the old
  "never a title" line was false. The new text says what is stored and why, and
  lists what genuinely never leaves the phone (files, messages, contacts,
  location, advertising ID, anything from the 18+ section).
- **Offline acceptance retried** (`legal_acceptance_service.dart`) — a local
  accept writes `legal_acceptance_pending_v1`; the server row is retried on the
  next launch and the flag clears only on a successful RPC. Agreeing in a tunnel
  no longer means the server never hears about it.
- **Update-required screen rebuilt as a clay poster**
  (`update_required_screen.dart`) — logo with a gold glow, `DIZZY` wordmark,
  "Update is required to use Dizzy", a keep-your-data line, a plain version
  pill ("You have v1.3.2 · Latest v1.3.7"), `Update now` → official latest
  release, and a quiet `Visit official page` link → `dizzy-by-sirius.netlify.app`.
  `PopScope(canPop: false)`; no countdown and no fake urgency.
- **Android only** (`main.dart::_enforceForceUpdate`) — early-returns on
  anything that is not Android. The Windows build is a portable ZIP with no
  updater, so blocking it would be a dead end; Windows keeps the normal in-app
  self-update path and is never locked out.

### Version facts

- `pubspec.yaml` = `1.3.7+1039`; ABI overrides land at 3039 / 2039 / 5039, all
  above the 1036 floor that v1.3.5 installs treat as an upgrade.
- `LegalTerms.version` = `2026-11-26`, so every install — including 1.3.6 —
  sees the corrected text and the new one-tap deal exactly once.
- `_oauthUa` in `iptv_network.dart` bumped to `Dizzy/1.3.7`.
- `installer/windows/setup.iss` default bumped to `1.3.7`. CI already passes
  `/DMyAppVersion=$cleanVersion`, so this only affects local manual builds —
  and it was still saying `1.1.3`.

## The update campaign (owner gated, Android only)

A plain broadcast cannot say someone's name, so it reads like spam. This mode
resolves each token's `@username` and each token's own reported `app_version`,
then renders one of four lines per person, followed by the plain version pair
as the on-screen body.

### Copy (verbatim, English only, 8–10 words with the name in)

| id | title | body |
|----|-------|------|
| a | `{name}, your Dizzy is wearing old socks 😅` | `Tap to update — v{from} → v{latest}` |
| b | `{name}, something new just landed while you were watching` | `One tap to update — v{from} → v{latest}` |
| c | `{name}, don't let this old version hold you back` | `Update now — v{from} → v{latest}` |
| d | `{name}, we saved you a spot on the new Dizzy` | `Your update is ready — v{from} → v{latest}` |

Pattern = `fnv1a("campaign:user_id") % 4`, so the same person gets the same line
within a campaign even if the send is retried. A campaign id is single-shot for
20 hours: a second call answers `409 campaign_already_sent` and writes no rows.

### Audience before sending

```sql
select app_version, platform, count(*) as tokens
from public.device_tokens
where enabled
group by 1, 2
order by 1;
```

As measured on 2026-11-25 the old-build reach was: 1.3.2 → 0 tokens (it has no
push service), 1.3.3 → 2, 1.3.4 → 3, 1.3.5 → 4. That is **9 phones**, 8 of them
Android. 1.3.6 is current and is not a target. Re-run the query — this is a
number that moves daily.

### Send

Always dry-run first; `dry_run` counts the audience and sends nothing:

```powershell
$h = @{
  apikey        = $env:SUPABASE_ANON_KEY
  Authorization = "Bearer $env:SUPABASE_SERVICE_ROLE_KEY"
  'Content-Type'= 'application/json'
}
$body = @{ mode='update'; campaign='2026-11-26'; latest_version='1.3.7';
           android_only=$true; dry_run=$true } | ConvertTo-Json
Invoke-RestMethod -Method Post -Headers $h -Body $body `
  -Uri "https://<ref>.supabase.co/functions/v1/push-send"
```

Drop `dry_run` for the real send, once, with the owner watching.

### The 3-day block (D1)

Only after the release page serves v1.3.7 — blocking before the download page
carries the target version strands people on a poster with no new build behind
it. Set both keys through the audited RPC, never by editing the table:

```sql
select admin_set_config('min_app_version', '1.3.7');
select admin_set_config('force_after', '2026-11-29T00:00:00Z');
```

Between now and the deadline, old builds show the advisory banner with a
countdown (`HomeNoticeBanner`); after it, the poster (`UpdateRequiredScreen`).
Offline clients never block — they only have the key if the server reached them
once.

To lift the block immediately:

```sql
select admin_set_config('force_after', '');
```

`UpdateGate.evaluate` treats empty as "no deadline", so the banner returns and
nobody is locked out. Keep `min_app_version` only if the advisory is still
wanted; set it to `''` to remove the nudge entirely.

**Windows is not in this campaign.** `android_only: true` filters at send time
and `_enforceForceUpdate` returns early on Windows, so the one Windows device on
1.3.2 keeps working and updates itself through the portable ZIP path.

## Artifact pruning — do this every release

The stale-download problem is that an old asset URL keeps resolving at
`/releases/download/v<old>/…`, so a bookmark, a chat link, or a stale
`releases.json` can hand someone a build that is two releases behind and can no
longer be supported. The landing page itself points at `releases/latest`, which
is always right; the pruning is for every other link in the world.

After the new release is published and verified:

1. Keep the new release **and the immediately previous one** (rollback path).
2. Delete the binaries from every older release. Keep the release entry and its
   notes, so old links land on a readable "this build is retired" page instead
   of a 404 with no context.

```powershell
$keep  = @('v1.3.7', 'v1.3.6')
$tags  = gh release list --limit 50 --json tagName --jq '.[].tagName'
foreach ($tag in $tags) {
  if ($keep -contains $tag) { continue }
  $assets = gh release view $tag --json assets --jq '.assets[].name'
  foreach ($a in $assets) {
    if ([string]::IsNullOrWhiteSpace($a)) { continue }
    gh release delete-asset $tag $a --yes
  }
}
```

Then add one line to the retired release body so the page explains itself:

```powershell
gh release edit v1.3.5 --notes "Retired. Install the latest release: https://github.com/Sirius6907/Dizzy-v3/releases/latest"
```

Verify:

```powershell
gh release view v1.3.7 --json assets --jq '.assets[].name'   # full list
gh release view v1.3.6 --json assets --jq '.assets[].name'   # rollback, untouched
curl.exe -s -o NUL -w "%{http_code}`n" -L `
  https://github.com/Sirius6907/Dizzy-v3/releases/download/v1.3.5/Dizzy-v3-arm64-v8a.apk   # expect 404
curl.exe -s -o NUL -w "%{http_code}`n" -L https://github.com/Sirius6907/Dizzy-v3/releases/latest  # expect 200
```

Note `gh` writes progress to stderr, so PowerShell may print `Exit code: 1` on
a successful delete — read the output, not the code.

## Manual QA worth doing before publish

1. **First run** — clean install (or clear app data): P2P card → username →
   one-tap screen. Swipe down and tap outside: the sheet must not move or close.
   Accept: all five switches show on in Settings → Privacy.
2. **Re-prompt** — install over 1.3.6, turn two switches off in Privacy, launch:
   the sheet opens, says accepting re-enables everything, Accept → all five on.
3. **Offline accept** — airplane mode, fresh install, Accept, kill app, restore
   network, relaunch: `legal_acceptances` gains the row (local pref
   `legal_acceptance_pending_v1` clears).
4. **Withdrawal** — turn off Crash reports in Privacy, force a handled crash,
   confirm no crash row is written.
5. **Poster** — set `min_app_version = 1.3.7` and `force_after` to a past
   timestamp, launch 1.3.2/1.3.5: poster shows the logo, both version numbers,
   `Update now` opens the release page, `Visit official page` opens the site,
   back button does nothing.
6. **Windows exempt** — same config on a Windows build: no poster, normal
   self-update path.
7. **Campaign dry run** — the dry run reports ~9 targets and sends nothing;
   check `admin_push_events` has no row for a dry run if that is the intended
   behaviour (verify in the function before the real send).

## Publish sequence (owner-gated)

1. `git push origin prism/v2-reskin`
2. `git push origin v1.3.7` → `.github/workflows/build.yml` builds, verifies the
   release-key fingerprint, and publishes the release with 12 assets.
3. Verify: `gh release view v1.3.7 --json assets`, APK HEAD returns 200, and
   `releases/latest` resolves to v1.3.7.
4. Regenerate `site/releases.json` and deploy the downloads site (step 3 above).
5. Deploy DB → edge function (steps 1–2 above).
6. Prune old assets (keep v1.3.7 and v1.3.6).
7. Campaign dry run → real send → set `force_after` to start + 3 days.

## Rollback

- **App** — reinstall v1.3.6 assets; nothing in this release migrates client
  storage irreversibly (the pending-flag pref is additive and ignored by older
  builds). The legal version going backwards means 1.3.6 will not re-prompt.
- **Blocking** — `select admin_set_config('force_after', '');` takes effect on
  the next config pull (boot or the 6-hour heartbeat pull, 1-hour client cache).
- **Campaign** — irreversible once FCM accepts the tokens; that is why the dry
  run is mandatory and why the campaign id is single-shot.
- **Function** — redeploy from the `v1.3.6` tag; the `mode` field defaults to
  `test`, so old callers keep working.

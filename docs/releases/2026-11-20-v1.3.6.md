# v1.3.6 — "One App" (build 1038)

Tag: `v1.3.6` · commit `2abfe1d1` · branch `prism/v2-reskin` · 2026-11-20

This is the release where the pieces started behaving like one app: the brand
plays an intro, the music queue survives a restart, watch party got its last
two loose ends, and push stopped being a broadcast-only switch.

Same rules as every release so far: nothing is pushed, tagged remotely,
released, or deployed without the owner saying go. The tag in this repo is
local.

---

## What ships in the build

- **Brand intro** — 3.15 s halo → wordmark → line, played over Home (never
  gates boot), tap to skip, 620 ms fade under reduced motion, once per launch.
  Android launch theme and v31 splash are black now, so there is no white
  flash before the first frame.
- **Music queue persistence** — tracks, order and position are saved as you
  go and restored on next launch, paused at the same spot. Never autoplays.
- **Watch party** — voice quality High / Balanced / Data saver (48k / 24k /
  12k, all with echo cancellation, noise suppression and AGC), applied on next
  join; invite from inside the room with chat → share sheet → clipboard
  fallback; light-theme join sheet fixed.
- **Push controls (client + panel)** — one kill switch for every send, target
  resolution from a DIZ-code / device id / user id / @username, FCM 429/503
  retries with backoff, and an operator ledger (`admin_push_events`).
- Plus everything committed between `v1.3.5` and `v1.3.6` — see
  `CHANGELOG.md`. That includes profile identity blocks, foreground
  media/download service, telemetry and legal-acceptance plumbing, device
  cards in the admin panel, and the 18+ entry work.
- **The streaming work staged as 1.3.6+1037** — that bump was never tagged or
  released, so its extractor and anime-provider fixes ship here too. The
  changelog merges both bumps into one 1.3.6 entry. The work was planned as
  1.4.0; it ships as 1.3.6 so the number matches the bump that never left, and
  versionCode 1038 still upgrades v1.3.5 installs.

### Upgrade verified against the published build

The updater doing the work is **v1.3.5's** code, not v1.3.6's, so the proof has
to come from what v1.3.6 actually published:

- Android, same key: CI's `Verify release signing` gate passed against the
  pinned release-key fingerprint (`c513faef…`), so the APKs install over an
  existing v1.3.5 install and keep app data.
- Android, higher codes: `arm64-v8a` = **3038** (was 3036), `armeabi-v7a` =
  **2038** (was 2036), `x86_64` = **5038** (was 5036), Universal = **1038**
  (was 1036). Asset names are unchanged, so v1.3.5's picker resolves them.
- Windows: same `AppId` (`{9B8C7D6E-…}`), same per-user `PrivilegesRequired=lowest`,
  same `DefaultDirName`, installer stamped `1.3.6` from the tag. Inno upgrades
  in place; user data lives outside `{app}`.
- Rollout: release is non-prerelease and carries no `rollout_percent`, so
  `UpdatePolicy.parseRolloutPercent` treats it as 100% on the stable channel.

## Not live yet — owner-side deploy

The app builds and runs without these. The **push control panel** needs all
three steps; skipping them leaves the new panel section failing on missing
RPCs.

### 1. Database migrations (in order)

The push functions read through the device-card resolver, so the chain matters:

```powershell
supabase db query --linked -f supabase/migrations/20261120_admin_devices_username.sql
supabase db query --linked -f supabase/migrations/20261121_device_code_registry.sql
supabase db query --linked -f supabase/migrations/20261121_admin_device_telemetry.sql
supabase db query --linked -f supabase/migrations/20261121_device_logs_backfill.sql
supabase db query --linked -f supabase/migrations/20261121_legal_acceptance.sql
supabase db query --linked -f supabase/migrations/20261121_retention_and_installs.sql
supabase db query --linked -f supabase/migrations/20261122_admin_device_card.sql
supabase db query --linked -f supabase/migrations/20261123_admin_push.sql
```

`20261123_admin_push.sql` creates `push_settings`, seeds its single row
(`sending_enabled = true`), and defines `admin_push_audience`,
`admin_push_set_enabled`, `admin_push_resolve`, `admin_push_log` and
`admin_push_events`. It sends nothing by itself.

Skip any file already applied — this repo applies migrations with
`db query`, so `supabase migration list --linked` will not know about them.
Re-running a file is safe where it uses `if not exists` / `create or replace`,
but check before re-running the backfill ones.

### 2. Edge function

`supabase/functions/push-send/index.ts` now reads `push_settings` before every
send and retries 429/503. Redeploy it:

```powershell
supabase functions deploy push-send --project-ref <ref>
```

It keeps using the existing secrets: `SUPABASE_URL`, `SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`, `FIREBASE_SERVICE_ACCOUNT`. `push-brain` is
unchanged by this release but also honours the switch, so it needs no
redeploy.

### 3. Admin dashboard

`admin-dashboard/app.js` gained the push section (switch, audience count,
resolver, send, ledger). Redeploy to Netlify (`dizzy-s-admin`, site
`7c49d0a2-39ac-473e-ad24-996fddad593c`) after step 1, otherwise the panel
loads but the push tab errors on the missing RPCs.

## Manual QA worth doing before publish

1. **Intro** — cold start: intro plays over Home, tap skips it, second launch
   in the same run does not replay it. With Android "remove animations" on:
   fade, not sweep. No white flash before the first frame.
2. **Queue** — play a track, pause, kill the app, reopen music: same track,
   same position, still paused.
3. **Watch party** — join a room twice with different voice qualities; quality
   applies on the new join, not mid-call. Invite from room chat; simulate
   offline/rate-limited chat and confirm the share-sheet → clipboard fallback.
   Check the join sheet in Light Clay.
4. **Push** — admin panel: audience count renders; flip the switch off, send,
   confirm refusal and a ledger row; flip on, resolve a DIZ-code, send to one
   device; confirm the ledger shows who/where/how many.
5. **Regression pass** — profile identity block, account hub entry, now-playing
   card dismissal, media/download foreground service survival.

## Publish sequence (owner-gated)

1. `git push origin prism/v2-reskin` — **done**
2. `git push origin v1.3.6` → `.github/workflows/build.yml` builds and publishes
   the GitHub release with assets. — **done** (run `44704404931`, 12 assets,
   non-prerelease)
3. After the release exists: regenerate `site/releases.json`, commit it. —
   **done** (`205a6ea1`)
4. Deploy steps 1–3 above (DB → edge function → dashboard), in that order. —
   **pending owner**

## Rollback

- App: reinstall the `v1.3.5` assets from the previous GitHub release; no data
  migration in this release changes client storage irreversibly (queue save is
  additive).
- Push: set `push_settings.sending_enabled = false` — that is the switch, no
  redeploy. Edge function can be redeployed from the `v1.3.5` tag if the
  retry loop misbehaves.
- Dashboard: redeploy the previous Netlify build from the Netlify UI.

# Dizzy v1.3.3 → v1.6 Retention Program — Master Plan

> **Scope decision (2026-10-31, Sirius):** every phase below ships inside the
> same v1.3.3 update. No v1.4/v1.5/v1.6 cut; the version label stays 1.3.3
> while build numbers bump. Phase 0 is done (gate applied + verified, artifacts
> built, publish held for Sirius). Phase 1.1 is live (catalog v2, region=IN).

> **For agentic workers:** This is a program roadmap, not a single task list. Each phase gets its own task-level TDD plan (superpowers:writing-plans) at execution time, saved next to this file as `YYYY-MM-DD-<phase>.md`.

**Goal:** Ship v1.3.3 with mandatory usernames, then turn Dizzy into an India-first, taste-aware app whose notifications feel like the algorithm reads the user's mind.

**Architecture:** Three layers built in order — (1) identity truth on the server, (2) an event/taste pipeline that learns from real behaviour, (3) a push + notification brain that turns new, *playable* releases into short personalised nudges. Every layer is fail-soft and offline-first like the rest of the app.

**Tech Stack:** Flutter 3.x, Supabase (Postgres + RLS + edge functions, region Singapore), FCM (new), TMDB, JioSaavn edge proxy, Groq (free tier) for copy, admin dashboard (vanilla JS + realtime).

**Spec:** This document (program level). Phase-level specs are written when the phase starts.

## Global Constraints

- Exactly two themes: Light Clay / Dark Clay. Black text on light, white on dark.
- No secrets in `site/` or `admin-dashboard/` — both are public static.
- Migrations apply via `supabase db query --linked -f <file>` + manual `schema_migrations` insert. Never `db push --include-all`.
- No `git commit` / `git push` until Sirius explicitly confirms.
- Every network path fails soft; boot never blocks on cloud.
- Telemetry is consent-gated (existing `consents` table). Notifications are opt-in with quiet hours available.
- Per phase gate: `flutter analyze --no-pub` clean + full `flutter test --no-pub` green + screenshots in both themes.
- Notification copy: no free-form user data ever leaves the device; copy is generated from catalog metadata only.

## Phase 1 — India-first discovery + search (v1.4-A, target: 4–5 days)

**Problem today:** `supabase/functions/catalog/index.ts` only knows `trending|popular|top_rated`, passes no `region`, so TMDB answers with US defaults — exactly why Hollywood fills the home page for an Indian audience.

| # | Step | Notes |
|---|---|---|

| 1.2 | Anime + music feeds: AniList/Jikan for new episodes, existing `music-source` for JioSaavn new releases; cache both in `catalog_cache` | server-side only, no keys in client |
| 1.3 | Home composition policy: rows ordered by taste and recency, not provider defaults; existing `lib/services/discover/discover_service.dart` + `history_rail_policy.dart` become the client half of the ranking | keep `_injectSimilarSections` contract |

**Acceptance:** a fresh Indian profile sees ≥ 7/10 Indian/Hindi/anime titles on home; searching `pathaan` returns it #1; searching a misspelling still works; cache warm serve < 80 ms.

## Phase 2 — Event pipe + taste engine (v1.4-B, target: 5–6 days)

Without this, "algorithm reads my mind" is impossible; it is also the data source for notification targeting.

| # | Step | Notes |
|---|---|---|
| 2.1 | `events` table: `user_id`, `kind` enum (`impression`, `click`, `play_start`, `play_25`, `play_75`, `complete`, `search`, `notif_open`, `notif_dismiss`), `surface`, `tmdb_id`/`media_type`, `lang`, `genres[]`, `ts`; batched client queue (max 50, flush on resume) | consent-gated; enum-only, no titles of personal content |
| 2.2 | `taste_profiles` build (SQL + cron): recency-weighted affinity for genres, languages, decades, actors/directors, plus "avoid" set from early skips | inputs: events, `cloud_sessions`, my list, Trakt/Simkl ratings when linked |
| 2.3 | `recommend_for_me(p_surface, p_limit)` RPC/edge: ranked cards + `reason_code` (e.g. `because_you_watched`, `new_in_hindi`, `trending_in_odisha`) | p95 < 150 ms, cached 15 min per user |
| 2.4 | Cold start: 5-tap taste picker (languages + genres) shown once after the username gate; writes initial `taste_profiles` | skip-able, never blocks home |
| 2.5 | Admin: taste inspector ("why am I seeing this"), coverage + sparsity metrics | `admin-dashboard/app.js` new card |

**Acceptance:** two devices with different histories get demonstrably different top-10 rows; a title is never recommended after `complete`; reason codes render in the UI.

## Phase 4 — Notification brain (v1.5-B, target: 6–8 days)

| # | Step | Notes |
|---|---|---|
| 4.1 | `release_candidates`: daily ingest of new titles for IN/hi/en/regional + anime episodes + music releases. **Hard gate: only titles the app can actually play** (addon/Cinemeta probe or curated allowlist) | trust rule — never announce something unplayable |
| 4.2 | Personaliser: score = taste match × novelty × trending-in-region × completion affinity, minus already-watched / on-list / already-sent; kids + adult gates applied | one row per user per day max |
| 4.3 | Copy engine: template first, Groq LLM optional. 1 line + short note, Zomato/Netflix voice, Hinglish or English by device locale, ≤ 90 chars, facts only from metadata. Fallback templates when quota is out | admin tone library + preview |
| 4.4 | Cadence policy: default 1/day, max 3/week; best-time window from heartbeat data (evening 19:00–22:00 IST); auto-mute a pack after 5 ignores; packs = new releases, "you may like", "random pics for you", weekend binge, late-night anime | all overridable per user |
| 4.5 | Notification Center upgrade: server-backed inbox, unread badge, "why this" line, dismiss/done actions | replaces local-only inbox |
| 4.6 | Measurement: `send_log` → open rate, dismiss rate, mute rate, per-pack and per-copy-variant dashboards | admin analytics card |

**Acceptance:** 20-test-device pilot holds the 3/week cap; every notification has a real playable target; open-rate dashboard populated; mute after 5 ignores works; copy never exceeds 90 chars.
